## Question and contribution

Given that OLMo chooses a wrong answer to a PopQA question, can subject–candidate training-text proximity predict **which wrong candidate wins** on previously unseen subjects, beyond a candidate's general tendency to be chosen? The 2023 [Kang and Choi co-occurrence paper](https://aclanthology.org/2023.findings-emnlp.518/) already established the broad idea. A contribution here would require out-of-sample wrong-choice prediction, reliable entity/relationship measurement, and a gain over strong baselines. A positive coefficient in an all-choice regression is insufficient.

2. **Wrong-choice evaluator.** Implement a grouped choice model restricted to questions where the LM's top candidate is non-gold; exclude the gold row. Compare an identity-only baseline against identity plus subject–candidate co-occurrence. Candidate intercepts absorb each answer's overall popularity, corpus marginal, spelling, and mean token-length tendency. Fit only on development questions. Use question-level log loss, top-1 accuracy and true-winner rank on held-out errors. Add a paired question bootstrap for the log-loss difference. 3. **Measurement and plausible-answer audit.** Record window hit counts, retrieval failures, ambiguous names, alias decisions, subject-in-answer overlap, and evidence of actual subject–answer relations. Two people independently label a blinded sample of candidate windows and plausible alternatives. Gate: agreement and precision are reported, and label-ambiguous questions are excluded by a written rule. If the corpus measure is mostly false matches, replace it before confirmation. Estimate: 1–2 human days plus bounded free API queries.
4. **Fresh confirmation.** Use PopQA `occupation` as a separate relation. It has 532 questions, 532 subject IDs and 84 raw answer IDs in the pinned TSV. Its labels can be multi-valid, so step 3 is mandatory. Freeze normalized-subject splits, the candidate pool, exclusions, model revision, prompt, count sampling, baselines, hyperparameter search, and analysis before any held-out answers are scored. The old country test is permanently exploratory. Score development first; choose regularization on development only. Score each fresh test question once. Gate: complete candidate grids, no normalized-name overlap, enough wrong dev/test questions for a stable estimate, and precommitted protocol. If any gate fails, report an inconclusive or blocked study. Estimate: 1–3 free-GPU days for scoring plus potentially tens of hours of infini-gram requests at a conservative rate. The API must not be hammered.
5. **Presentation.** Show a per-question table with the chosen wrong answer, its gold answer, its proximity rank, baseline and augmented probabilities, and independently reviewed ambiguity. Report absolute held-out log-loss gain and its interval, not just a coefficient. Include all failures and a reproducible row bundle. Gate: another person can rerun the offline evaluator from a clean checkout. Estimate: half a day.

## New confirmation protocol, locked before any `occupation` scoring

This is a protocol for a future run, not a claim that the run happened. The experiment remains **blocked** until the semantic-label audit is done and the protocol is committed. The pinned PopQA file is revision `098765c79ea10a2cb19c828324e33281b8336ec0`, SHA-256 `9a5227f41bff0e4c331d4a774d946b12f95307892b58f860a9606ef356e6089b`.

The unit is a question. Development and test must be split by normalized subject *string*, keeping all IDs for a normalized string together. Candidate answers are all distinct `occupation` gold IDs, with a pre-scoring equivalence/validity review. Every candidate whose normalized primary name appears in the question's PopQA `possible_answers` is initially treated as valid, alongside the designated gold ID. Human review may add further valid occupations before confirmation. If both-reader adjudication rejects the designated gold, exclude that question by the precommitted blind rule and publish its ID and reason; do not choose exclusions from model scores. The primary target is the LM's chosen **non-valid** answer among non-valid candidates, conditional on an error under that rule. This target is distinct from overall error probability.

**Development diagnostic amendment, 2026-11-14 Pacific time, before occupation scoring.** A bounded pilot may score 12 development question IDs selected by the SHA-256 order of `pilot:<question ID>`, with the four frozen demonstrations and all 84 primary-name candidates. It may sample at most 10 occurrences per subject, serially at 0.45 API requests per second with one attempt and a local response cache. This pilot is for scorer, API and label inspection only. Its tiny, noisy results cannot validate H1 or tune the fresh test protocol. The original 50-window confirmatory design remains a separate future run. No test IDs may be loaded by the model or the count client.

The primary comparison is an L2-regularized conditional softmax with candidate-identity intercepts versus the same model plus `log1p` estimated subject-window co-occurrence. The common identity intercepts absorb stable candidate-specific tendencies. A feature constant across candidates in a question cannot help either model. Regularization is selected only by grouped development cross-validation, using candidate grids and subjects as inseparable units. The primary evaluation statistic is mean per-question negative log probability of the actually chosen wrong candidate; report baseline minus augmented, so positive means improvement. Secondary metrics are top-1 accuracy and percentile rank of the winner. Use 2,000 paired **normalized-subject cluster** bootstrap draws for an interval. A confirmatory success requires the lower 95% bound on the log-loss improvement to exceed zero, adequate audited measurement quality, and a complete untouched test evaluation. Otherwise the result is inconclusive or negative.

**Final lock pending.** Development outcomes caused the explicitly dated label and probe amendments below. Before any `occupation` test scoring, finish the human reviews and development measurement checks, then write and commit a new dated final preregistration that freezes the exact valid-answer sets, exclusions, corpus feature, prompt, model, regularization selection and test command. If the API cannot support the planned coverage, if human labels disagree materially, or if development performance does not justify the test, stop and report the negative/inconclusive development result. Do not repurpose the 421 test questions for tuning.

Pre-specified failure checks: candidate-identity-only baseline; shuffled subject-to-co-occurrence assignments within candidate (development diagnostic only); original hit fraction and `log1p` count sensitivity; primary-name-only versus validated aliases; answer-length normalization; prompt paraphrase on development. No substitution mechanism or causal training-exposure conclusion follows from predictive gain. A stronger semantic-plausibility baseline is mandatory for a novelty claim and requires the blinded human ratings in step 3. Do not interpret an identity-baseline gain alone as proof of novelty.

### Post-pilot label amendment, 2026-11-14 Pacific time

The first 12-question development pilot used the designated PopQA object ID alone and called 9 choices wrong. Before any `occupation` test scoring, the public `possible_answers` field showed that the model's choice `actor` for question 6173288 is explicitly accepted even though its designated object is `screenwriter`. The initial single-gold count overstates errors. The evaluator now requires `is_valid`, excludes all accepted candidate rows from wrong-choice sets, and skips questions whose chosen answer is accepted. The initial pilot output is preserved as `initial_single_gold_results.json`; the corrected pilot reports both counts. This change was prompted by **development outcomes** and is not portrayed as a pristine preregistration. The fresh test remains unopened, and human semantic review is still required.

**Development extension, after the pilot and before any new scoring.** Score all 111 development questions against the frozen 84-name pool with the pinned checkpoint and four frozen demonstrations. Record dataset-designated and `possible_answers` validity separately. This determines whether enough development errors exist for the conditional model and creates a blinded review target list. It uses no new corpus API calls and cannot support a held-out claim. Do not use these outcomes to revise the fresh test protocol without a dated amendment.

**Corpus development extension, after full dev scoring and before any new context requests.** The model has 80 `possible_answers`-defined development errors. Select 30 of those error question IDs by the SHA-256 order of `count-probe:<question ID>`. For each, retrieve up to 50 subject windows, primary-name candidate matches only, 200 index tokens maximum, a single API attempt, and at most 0.45 requests per second. Cache and resume per subject. Reject blocked windows. Compare candidate-identity and identity-plus-proximity models by three-fold development cross-validation. The CV difference is exploratory and cannot be used as a confirmatory interval or to tune the fresh test. Its purpose is to detect a useless or mismeasured signal before asking humans to adjudicate the full study.

**Identity-baseline development check, 2026-11-14 Pacific time.** On all 80 currently dataset-defined development errors, fit candidate intercepts only. Select the L2 penalty from `[0.01, 0.1, 1.0]` with three-fold normalized-subject cross-validation and report out-of-fold log loss, top-1 accuracy and mean rank. Compare with uniform choice among non-valid candidates. These are provisional labels pending human review and do not involve corpus proximity or a held-out result.

**Development grid amendment, after the first identity-only CV.** The baseline selected the lowest available penalty, `0.01`, with out-of-fold log loss `2.2645`, so the original grid did not bracket its optimum. Preserve that initial result and extend the common identity/augmented penalty grid to `[0.0001, 0.001, 0.01, 0.1, 1.0]`. Refit only the development identity baseline. This is development tuning, not a preregistered discovery or a test-set decision.

**Identity-baseline outcome.** The amended grid selected `0.001` with three-fold development out-of-fold log loss `2.2419756`, top-1 `24/80`, and mean chosen-label rank `5.5375`; uniform wrong-choice loss is `4.4156475`. All 80 provisional error questions have distinct normalized subjects. The grid and per-question predictions are stored in `results/occupation_dev_identity_baseline/`; the original three-value output is stored as `initial_grid_results.json`. Because the same folds selected the penalty, these are descriptive development numbers. There is no corpus feature in this run. The final test protocol and human-validity gate are still pending.
